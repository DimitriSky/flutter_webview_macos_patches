# Повторы клавиш в macOS WebView. Часть 2: B1, B2 и B3

Дата: 2026-09-25. Обновлено: 2026-09-26.
Статус: исследование в отдельном тестовом приложении.
Это продолжение `2026-09-25-macos-webview-key-repeat-research.md`, а не
описание уже установленного исправления TalkTo.

Код и raw-state лаборатории теперь находятся в `webview_key_guard/example/`.
Контрольный коммит `d457ed0` относится к прежнему отдельному репозиторию;
его история не импортирована в пакет. Документ описывает исторические прогоны,
а персональные пути в нём заменены нейтральными обозначениями.

Последний физический контроль: **B3 без диагностических подмен WebKit
получил 31 DOM событие, 0 дублей**. Шесть Shift+Escape, по два Cmd+B
и Cmd+Enter, Escape, Alt+Escape и Alt+Shift+Escape доставлены ровно
по числу нажатий. Удержание Enter дало первое событие и 17 нормальных
автоповторов; после отпускания события прекратились.
Новая граница действительно сработала семь раз: на каждом Shift+Escape
и одном Escape. Это подтверждает работу решения без подмен методов
WebKit и без подавления нормального удержания. Проверка нативной отмены,
соседних native controls и оставшегося физического покрытия еще впереди;
production TalkTo не менялся. Предыдущий D без подмен WebKit давал
66 дублей, B2 также не решал физический Shift+Escape.

## Короткий ответ о B2

B2 лидировал в автоматических проверках **встроенного** WebView, но
ручная проверка физической клавиатурой выявила сбой. В его полном автоматическом
прогоне 844 отправленные комбинации дали 844 DOM `keydown`, 0 дублей и
0 аварийных остановок. `Cmd+A`, Undo и Redo реально меняли значение HTML
input; 20 переходов из Flutter-поля в WebView с `Cmd+B` также прошли без
дублей.

Дополнительный отсекатель B2 при этом показал `suppressed: 0`. Это значит,
что во время этих успешных прогонов он **ни разу не встретил повторный вход
того же объекта NSEvent во Flutter при фокусе WebView**. Он не был выключен:
его условие просто не наступило. Чистый прогон показывает поведение всего
B2 в данных условиях, но **не доказывает**, что отсекатель остановит редкий
цикл B1, потому что именно этот цикл под B2 не был воспроизведен.

В физическом прогоне `Cmd+Enter`, `Cmd+B` и `Alt+Escape` дали по одному
DOM `keydown`. Затем один `Shift+Escape` дал 255 DOM `keydown`, из них
254 дубля. Аварийный ограничитель остановил run после 256 посещений
одного события в WebKit; `restartRequired: true`. B2 отсекает повторный
вход только во Flutter, а здесь было одно посещение Flutter и цикл внутри
`WKWebView.performKeyEquivalent`. Поэтому `suppressed: 0` и B2 **не
решает этот случай**. До нового решения тестировать клавиши в этом run
нельзя.

Это не означает, что сам механизм Flutter-отсекателя неверен. Отдельный
native XCTest передает ему один и тот же объект дважды: первый вход
проходит, второй отсекается; ввод вне WebView проходит. Отдельный тест
ledger подтверждает, что новый объект и легитимный repeat не считаются
тем же самым объектом. Unit-тесты не воспроизводят цепочку macOS.

## Что именно считаем

| Термин | Здесь означает | Не означает |
| --- | --- | --- |
| `NSEvent` | Нативный объект macOS для конкретного события клавиатуры | Просто название клавиши или сочетания |
| DOM `keydown` | Событие, дошедшее до JavaScript внутри HTML-страницы | Все посещения нативных обработчиков |
| `suppressed` | Сколько проходов остановила стратегия в данном run | Сколько ошибок исправлено или предотвращено в будущем |
| Идентичность события | Повторно встретился **тот же объект** `NSEvent` | Быстро нажата та же клавиша еще раз |
| Фокус WebView | `WKWebView` находится в нативной цепочке `firstResponder` | Только accessibility-фокус, видимый автоматизации |
| Run | Один режим и один экземпляр тестовой страницы с уникальным ID | История всех запусков вместе |

Удержание клавиши создает легитимные события `repeat`, а новое быстрое
нажатие создает новый объект. B2 не использует задержку по времени и не
должен отбрасывать эти события только потому, что сочетание совпадает.

Важно смотреть **оба** уровня. В сбойном запуске B1 страница показывала
0 DOM-дублей, но нативная обработка одного `Cmd+B` дошла до аварийного
предела 256 проходов. Поэтому надпись `duplicate 0` сама по себе не
означает, что цикл устранен.

## От первого обхода до B2

1. В production TalkTo сейчас находится `WebViewCommandKeyRouter.swift`.
   Он дает WebView сначала обработать событие, а для `Cmd+Enter` затем
   возвращает macOS ответ «обработано». Это останавливает повторную
   передачу **этой** комбинации. Другие клавиши он не исправляет;
   контрольный режим A лаборатории показал повторения на `Cmd+B`.
2. Режим B направлял `keyDown`, `keyUp` и смену модификаторов мимо
   стандартной обработки Flutter, когда сфокусирован WebView. В полном
   прогоне он получил 15 DOM-дублей на `Shift+Escape`.
3. B1 оставил такую маршрутизацию только для `keyDown`. `keyUp` и
   `flagsChanged` снова идут обычным путем Flutter. Это позволило пройти
   полную безопасную матрицу без DOM-дублей, но позже возник нативный цикл.
4. C и C2 пробовали отсеивать повторные объекты на границах WebKit.
   C2 прошел матрицу без дублей, но `Cmd+A` не выделил текст, а Undo не
   отменил ввод. Чистый счетчик клавиш оказался недостаточным критерием.
5. B2 - это B1 плюс проверка повторного входа **того же `NSEvent` на входе
   Flutter**. В отличие от C2, B2 не отсекает повторные посещения
   `WKWebView.performKeyEquivalent` до выполнения редакторской команды.

Все варианты используют системный `WKWebView`. Движок браузера не менялся;
менялись маршрут события и место проверки. Flutter SDK и движок Flutter
не патчились. Отдельное нативное окно D показало чистый автоматический
прогон, но пользователь пока выбрал исследование встроенного WebView.

## Как устроены B1 и B2

В лаборатории `LabFlutterViewController` наследуется от
`FlutterViewController`. Когда нативный фокус принадлежит WebView, B1 и B2
передают `keyDown` следующему нативному обработчику, не вызывая
`super.keyDown` и не отправляя это событие в обычный Flutter-маршрут:

```swift
if strategy.routesWebViewOutsideFlutter && webViewHasFocus {
  nextResponder?.keyDown(with: event)
  return
}
super.keyDown(with: event)
```

Если фокус в обычном Flutter-поле, остается штатная обработка Flutter.
В B1/B2 `keyUp` и `flagsChanged` также остаются штатными. Это важное
отличие от B, где маршрутизировались все три типа событий.

Перед маршрутизацией B2 записывает объект события в `EventLedger`.
Ledger использует слабую таблицу с проверкой идентичности указателя
`NSEvent`, а не сравнение текста, keyCode или времени:

```swift
let seen = flutter.record(event)
if strategy.guardsFlutterIdentity && webViewFocused && seen {
  suppressed += 1
  return false
}
return true
```

Первый проход конкретного объекта допустим. Второй проход **того же
объекта** при фокусе WebView прекращается до повторной маршрутизации.
Отдельный новый `NSEvent` с тем же `Cmd+B` должен пройти. Код: `macos/
Runner/Lab/KeyStrategies.swift`, `LabFlutterViewController.swift`,
`KeyboardExperiment.swift`, `EventLedger.swift` внутри лаборатории.

Для диагностики лаборатория подменяет методы `WKWebView` и записывает
посещения `performKeyEquivalent` и `keyDown`. B2 **не включает** проверки
C2, которые блокируют эти посещения, но диагностическая подмена и общий
аварийный ограничитель все равно присутствуют в тестовом процессе.
Следовательно, при переносе B2 в TalkTo нужно отдельно проверить его без
лабораторной диагностической обвязки и взаимодействие со старым
`WebViewCommandKeyRouter`. Нельзя механически наложить два обхода и
объявить результат проверенным.

## Как проверяли

- Изолированное приложение `WebView Key Lab`, bundle ID
  `com.dmilab.webviewkeylab`, Flutter `3.47.5` с T7,
  `webview_flutter 4.14.1`, `webview_flutter_wkwebview 3.26.1`.
- Одна локальная диагностическая HTML-страница с Prompt, HTML input и
  `contenteditable`. Страница считает DOM `keydown`, ввод и дубли;
  нативная трасса отдельно считает посещения WebKit/Flutter и объекты.
- Сервер диагностики внутри лаборатории слушает свободный порт на
  `127.0.0.1`. `/state` содержит текущий run, `/matrix` - матрицу.
  Порт не постоянный; PID и `bundlePath` проверялись перед UI-прогонами.
- Автоматизация сначала видела accessibility-фокус Prompt, но не
  активировала нативное окно: клавиши не доходили ни до native-трассы,
  ни до DOM. Координатный click в Prompt перед каждой комбинацией
  активировал окно. Пустой ранний прогон **не считался успешным**.
- Матрица: 74 клавиши x 16 наборов Cmd/Ctrl/Alt/Shift = 1184 случая.
  Автоматически отправлены 844 безопасных; 340 системных и оконных
  сочетаний сознательно оставлены для контролируемой проверки.
  Восемь вариантов `equal` без Shift инструмент отправлял как
  Shift+Equal. Значит, 844 попытки покрывают 836 различных ожидаемых
  DOM-сочетаний, а не все 1184.
- JavaScript определял диагностический дубль по timestamp, code,
  модификаторам и repeat. Нативный ledger отдельно проверял идентичность
  `NSEvent`. Повторный заход в WebKit сам по себе не считался багом:
  нормальное событие иногда посещает его несколько раз, но дает один
  DOM `keydown`.
- При 256 нативных посещениях одной сигнатуры лаборатория аварийно
  останавливает run. Это **провал теста**, а не успешная защита стратегии.
- `flutter analyze`, 5 Dart-тестов, 6 native XCTest и debug macOS build
  прошли. XCTest проверяет политику стратегий, но не реальную доставку
  клавиши операционной системой.

## Что пока нельзя заключить

- **B2 не исправил все клавиши.** Физический `Shift+Escape` вызвал цикл
  в WebKit. Также проверены 844 безопасные попытки автоматическим вводом,
  но не все системные команды. Удержание, отпускание модификаторов, другая
  раскладка, IME, Copy/Cut/Paste и форматирование rich text еще требуют
  целевой проверки.
- **Дополнительная защита B2 не спасла от физического сбоя.**
  В живых прогонах `suppressed: 0`. Unit-тест подтвердил ее правило,
  но физический цикл остался в WebKit, не возвращаясь во Flutter.
  Прямого воспроизведения именно B1-сбоя под B2 пока нет.
- **Нельзя считать Flutter единственным источником дублей.** Старый B
  дал 15 дублей на `Shift+Escape`, хотя максимум посещений Flutter для
  одной сигнатуры был 1, а WebKit посещался до 17 раз. B2 отличается
  от B маршрутизацией только `keyDown`, поэтому этот сбой не переносится
  на B2 автоматически, но и Flutter-guard не является универсальной
  защитой от всех маршрутов WebKit.
- **Идентичность объекта не покрывает новые объекты.** В отдельном
  нефокусированном прогоне C с `Alt+Escape` каждый проход имел новый
  `NSEvent` и timestamp 0. Такой случай guard B2 не распознает.
  Тот прогон не доказывает, что физическое `Alt+Escape` в правильно
  сфокусированном WebView ведет себя так же.
- **TalkTo не переведен на B2.** Сейчас в production остается узкий
  обход `Cmd+Enter`. Проверки относятся к отдельной лаборатории.

## Продолжение: источник повторного вызова, без нового workaround

### Что уточнили в старом физическом журнале

В `b2-physical-shift-escape-loop-2026-09-25.json` сохранены последние
512 нативных записей. Единственный вход данного `Shift+Escape` во Flutter
стоит на позиции 505 (нумерация с нуля). Перед ним уже есть 166 входов
того же события в `WKWebView.performKeyEquivalent` и еще один вход
служебного Escape с timestamp 0. У повторяемого события WebKit возвращал
`handled`; диагностический wrapper сохранял этот результат.

Это уточняет прежнее объяснение: **в данном физическом run цикл уже шел
до `LabFlutterViewController.keyDown`**. Нельзя утверждать, что его
запустил вызов `nextResponder.keyDown` из B2. Отсекатель на входе Flutter
не встречал эти ранние повторы. Сам хвост журнала не показывает, кто
вызвал первый повтор; полной причины он не доказывает.

### Что добавлено в лабораторию

Это новая диагностика, а не B3 и не очередной фильтр сочетаний.

- `NativeKeyTrace.swift` сохраняет последние 512 записей, первые 96 записей
  run и первые 32 записи каждого из последних 32 событий. Начало быстрой
  петли теперь не исчезает из-за заполнения кольцевого журнала.
- Для Escape сохраняются стеки первых трех, 16-го и 128-го вызовов
  выбранных обработчиков, цепочка нативных получателей и глубина
  `performKeyEquivalent`. Общий предел - 64 стека.
- `observedMs` измеряет момент входа в обработчик. Нативный
  `NSEvent.timestamp` и DOM `event.timeStamp` остаются отдельно: это
  время возникновения события, а не время каждого его повторного вызова.
- JavaScript сохраняет первые 32 и последние 12 `keydown`, а также
  `sincePreviousMs` и `sinceFirstMs` для повторяемого события. Никакой
  задержки, debounce или подавления событий в B2 не добавлено.
- `KEY_LAB_TRACE_STACKS=off` отключает сбор стеков.
  `KEY_LAB_WEBKIT_OBSERVATION=off` при **запуске нового процесса**
  полностью отключает подмену методов WKWebView. Маршрутизация и guard
  B2 при этом остаются. Snapshot явно указывает оба режима.
- Без подмены отсутствует и WebKit-часть аварийного ограничителя.
  Нулевые счетчики WebKit в таком запуске означают отсутствие измерения,
  а не отсутствие повторов. Режимы A/C/C2 зависят от этой подмены:
  такой контроль предназначен для B1/B2 и D.

Пример запуска контрольного B2 из корня лаборатории, только после
закрытия предыдущего процесса:

```bash
KEY_LAB_WEBKIT_OBSERVATION=off \
  "build/macos/Build/Products/Debug/WebView Key Lab.app/Contents/MacOS/WebView Key Lab"
```

Сбор стеков влияет на длительность обработки. Даже полученные новым
журналом интервалы нельзя выдавать за скорость работы без диагностики.
Текст полей не включается в нативную трассу; `capture_run.rb` по-прежнему
заменяет значения полей их длиной в сохраняемом evidence.

### Новый контрольный автоматический прогон

Среда: macOS 26.4.1 (25E253), системный WebKit
`21624.1.16.11.4`, тот же Flutter 3.47.5 и plugin 3.26.1.
Изолированное приложение проверено по пути, PID 54734 и диагностическому
URL `http://127.0.0.1:56794`. Run `1790361203679068`.
Один автоматический `Shift+Escape` дал один DOM `keydown`, 0 дублей,
один вход Flutter, `suppressed: 0`, без аварийной остановки.

Стеки показали две разные нормальные ветки:

```text
WebKit executeSavedCommandBySelector
  -> NSWindow doCommandBySelector
  -> NSWindow _cancelKey
  -> WKWebView.performKeyEquivalent
     (служебный Escape: timestamp 0, modifiers 0, unhandled)

WebKit doneWithKeyEvent
  -> NSApplication.sendEvent
  -> NSWindow.sendEvent -> WKWebView.keyDown
  -> LabFlutterViewController.keyDown -> NSWindow.keyDown
  -> WKWebView.performKeyEquivalent
```

### Гипотеза, которую теперь можно проверить

В исходниках WebKit есть специальная ветка против повторной интерпретации
Escape, пришедшего через команду отмены. Ее условие требует отсутствия
независимых от устройства модификаторов. В другом месте WebKit помечает
событие как повторно отправляемое только на время синхронного
`NSApp.sendEvent`; это отдельный механизм.
[WebKit, performKeyEquivalent](https://github.com/WebKit/WebKit/blob/WebKit-7624.1.16.11.4/Source/WebKit/UIProcess/mac/WebViewImpl.mm#L5891),
[WebKit, doneWithKeyEvent](https://github.com/WebKit/WebKit/blob/WebKit-7624.1.16.11.4/Source/WebKit/UIProcess/mac/WebViewImpl.mm#L5197).

Проверяемое предположение: физический Shift+Escape повторно попадает
в WebView через выполнение команды отмены, когда первая защита не
подходит, а вторая еще не действует. **Стек именно сбойного физического
вызова пока не получен; это гипотеза, не установленный дефект WebKit.**
Публичный tag имеет совпадающий суффикс версии с системным framework,
но не заменяет исследование установленного бинарного файла.

Apple описывает отдельные маршруты для клавиши, сочетания и команды
отмены. В старом обсуждении WebKit отдельно отмечено отличие
моделирования Escape от обработки настоящей клавиши; это полезный
контекст, а не доказательство нашего сбоя.
[Apple: Handling Key Events](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/HandlingKeyEvents/HandlingKeyEvents.html),
[WebKit 165593](https://bugs.webkit.org/show_bug.cgi?id=165593).

На момент первого автоматического контроля физический Shift+Escape
с новыми стеками еще не был получен; последующее воспроизведение
описано ниже. Контроли D с физической клавиатурой и B2 без подмены
WKWebView остаются следующими сравнениями на свежих процессах.
Новый workaround, изменение Flutter SDK и изменение production TalkTo
в этом продолжении не выполнялись.

## B3: граница между нажатиями и исполнением команд

Нажатие и команда - разные этапы. Например, WebKit сначала доставляет
Escape странице, затем передает неиспользованную команду отмены AppKit.
Проблемный обратный маршрут из предыдущих стеков возвращает событие в
исходный WebView, где оно снова интерпретируется как клавиатурный ввод.

Кандидат B3 сохраняет маршрутизацию B2 и добавляет временную **по стеку
вызовов, не по таймеру** область исполнения команды. Пока `NSWindow`
исполняет `doCommand(by:)` при фокусе WebView, исходный host не принимает
обратно тот же объект события как key equivalent. Возвращается `false`,
то есть «этот host не обработал сочетание», а не ложное подтверждение
выполнения команды. Остальная обработка AppKit остается доступной.

Когда вызов команды завершился, ограничение полностью снято через
`defer`. Новое событие, обычный автоповтор, другое окно и тот же объект
вне этой команды не отбрасываются. Нет фильтра Shift+Escape, списка
запрещенных клавиш, debounce, изменения JavaScript или патча Flutter SDK.

Новый owner: `macos/Runner/Lab/WebCommandBoundary.swift`.
Он содержит per-window scope, обрамляющий NSView, небольшой host-controller
и override окна. В B2/остальных режимах scope не активируется; D остался
обычным отдельным NSWindow. Контекст и счетчики команды видны в
`native.commandRouting`, записи - в `window.command.in/out` и
`command.equivalent.skip`.

Reuse audit:
- needed: отделить обратный поиск сочетания от уже исполняемой команды;
- candidates found: B2, C2, имеющийся TalkTo Cmd+Enter router;
- decision: extend B2, create separate AppKit command-boundary owner;
- why: глобальный запрет повторных объектов C2 ломает редактирование,
  а Cmd+Enter router относится только к одной комбинации.

Размеры до изменения: MainFlutterWindow 26, KeyStrategies 77, LabBridge
44, variant.dart 15, RunnerTests 129 строк. Новый owner планировался
до 150 строк; bootstrap остается только сборкой компонентов.
Уровень проверки - Level 1: native tests, Dart tests/analyzer, живая
матрица и физический контроль исходного сбоя, без нового DevControl.

На этой стадии подтверждено:

- `flutter analyze`: чисто; `flutter test`: 5 тестов;
