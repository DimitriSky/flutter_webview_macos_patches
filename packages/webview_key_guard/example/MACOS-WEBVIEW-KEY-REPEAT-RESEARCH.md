# Flutter / macOS WebView: исследование повторных клавиатурных событий

Дата среза: 2026-09-25. Тэг: `macos-webview-key-repeat`.

## 1. Краткий итог

Одно нажатие клавиш внутри страницы иногда превращается в множество
повторных событий. Если страница отправляет запрос по этому сочетанию,
пользователь видит множество отправок. Это не обязательно повторное
срабатывание команды отправки самого TalkTo: повтор может происходить
внутри WebView, до бизнес-логики приложения.

Полного исправления для встроенного в Flutter WebView пока нет.
Создана лаборатория с исходным поведением и пятью переключаемыми подходами.
Из них наиболее убедительный результат у D: отдельное нативное окно macOS.
Это архитектурный обход проблемного взаимодействия, а не исправление Flutter engine.

- 0, без исправления: воспроизведён цикл на Cmd+Enter.
- A, исправление только Cmd+Enter: цикл остаётся на Cmd+B.
- B, изменение маршрута событий: остались повторы Shift+Escape.
- C, защита по идентичности события: остались дубли трёх сочетаний с Escape.
- D, отдельное нативное окно: 844 автоматических нажатия, ноль дублей.
- E, JavaScript preventDefault: ломает обычные команды редактирования,
  при этом цикл на Alt+Escape остаётся.
- Ни один вариант не сертифицирован полным ручным прогоном физической клавиатурой.
- Патч Flutter engine не реализован; необходимость такого патча не доказана.
- В рамках лабораторного сравнения код TalkTo не менялся.
- Этот документ фиксирует уже проведённое исследование; его запись не является
  новым прогоном тестов или внедрением варианта D в TalkTo.

## 3. Что было воспроизведено и на каких версиях

Проблема сначала наблюдалась в TalkTo. Ограниченный обход для Cmd+Enter
не оказался универсальным: пользователь физической клавиатурой
воспроизвёл повторы Cmd+B.

Затем повтор Cmd+Enter был воспроизведён автоматическим вводом в отдельном
минимальном Flutter-проекте, без бизнес-логики и shortcuts TalkTo.
Это показывает, что код команд TalkTo не является необходимым условием
воспроизведения. Но само по себе это не устанавливает виновный компонент:
Flutter engine, плагин, WebKit или их взаимодействие.

В предыдущем сравнении минимального проекта повтор сохранялся:

| Flutter | webview_flutter_wkwebview | Наблюдение |
| --- | --- | --- |
| 3.44.6 | 3.26.0 | Cmd+Enter воспроизводит повтор |
| 3.47.5 | 3.26.0 | Обновление SDK не устранило повтор |
| 3.47.5 | 3.26.1 | Обновление плагина также не устранило повтор |

Основной прогон лаборатории A-E:

| Flutter | 3.47.5 |
| Dart | 3.13.4 |

Сохранённые JSON предыдущего сравнения SDK находятся в `evidence/`.
Точный patch-level macOS не указан в кратком протоколе; его не следует
угадывать. При следующем воспроизведении нужно сохранить `sw_vers`.

Глобальный Flutter в ходе этого исследования не обновлялся:
новый SDK выбирался явным абсолютным путём.
Shorebird отдельно не тестировался. По этим результатам нельзя обещать,
что переход на Shorebird устранит проблему.

## 4. Что значит нативный WebView

WebView на macOS уже использует системный WKWebView, даже когда отображается
внутри Flutter. Это не выбор между «браузер Flutter» и «браузер Apple»:
меняется размещение и цепочка обработчиков клавиатуры.
См. [официальный пакет webview_flutter_wkwebview](https://pub.dev/packages/webview_flutter_wkwebview).

```text
Встроенный вариант:
окно приложения -> Flutter / platform view -> WKWebView

Вариант D:
отдельное NSWindow приложения -> WKWebView
```

Во втором случае окно принадлежит тому же приложению.
Это не Safari, не отдельная программа и не новый браузерный движок.
Flutter может отдавать команды Swift и получать события через
[platform channels](https://docs.flutter.dev/platform-integration/platform-channels).

Важно: native window должно действительно обходиться без Flutter-контроллера
в цепочке клавиатурных обработчиков. Просто открыть ещё одно Flutter-окно
с тем же встроенным WebView не равнозначно варианту D.

## 5. Как устроена лаборатория

У каждого запуска есть режим и уникальный run ID.
Переключение режима создаёт новый запуск; старые отчёты страницы и native-части
не должны примешиваться к новому. Предыдущий embedded view удаляется
перед созданием следующего.

В приложении есть:

- Шесть режимов: исходный 0 и пять подходов A-E.
- Flutter-поле для проверки перехода фокуса между Flutter и страницей.
- HTML-страница с textarea Prompt, обычным input и contenteditable.
- Счётчики событий, таблица сочетаний и сохранённые сводки сравнений.
- Stop, Refresh и аварийная остановка при цикле.
- Отдельное окно для D; D выбран начальным режимом для ручной проверки.

Диагностический HTTP-сервер встроен в тестовое приложение,
слушает только loopback и выбирает свободный порт.

| Endpoint | Назначение |
| --- | --- |
| GET /keys | Диагностическая HTML-страница |
| GET /keyboard.js | Учёт событий страницы |
| POST /events | Приём отчёта страницы |
| GET /state | Состояние запуска, native-метрики, результаты |
| GET /matrix | Запланированные сочетания |

В stdout выводится `KEY_LAB_URL=...`. Порт из старого запуска не является
постоянным адресом. PID и bundlePath в состоянии нужны для проверки экземпляра.
Страница не вызывает модель и не отправляет сообщения в backend TalkTo.
Её локальные POST /events являются диагностикой, а не повторными AI-запросами.

### Два уровня измерения

JavaScript считает keydown и диагностические дубли по сочетанию:

```text
event.timeStamp + event.code + modifiers + event.repeat
```

Нативная часть отдельно учитывает:

- Повторные посещения обработки по timestamp/keyCode/modifiers/isARepeat.
- Идентичность самого объекта NSEvent через слабую таблицу указателей.
- События, дошедшие до Flutter-контроллера, и события, направленные мимо него.

Повторный заход в нативный performKeyEquivalent сам по себе не доказывает баг.
AppKit может несколько раз пройти этот маршрут, доставив странице один keydown.
Поэтому native-счётчики и DOM-счётчики нельзя смешивать.

### Аварийная остановка

После 256 нативных посещений одной сигнатуры лаборатория останавливает
эксперимент и требует полный перезапуск приложения.
Это ограничитель последствий, не шестой способ исправления.

Число 256 относится к нативным посещениям, а не обязательно к 256 DOM-событиям.
Поэтому в некоторых циклах до остановки получалось 128 событий страницы.
После остановки переключать режим в том же процессе нельзя:
состояние очереди событий уже могло быть повреждено.

## 6. Варианты и примеры кода

Фрагменты ниже объясняют механизм. Это сокращённые схемы, не готовый
production patch; в настоящем коде есть проверка режима, учёт запуска,
метрики и аварийный ограничитель.

### 0. «Без фикса»

Обычный embedded WKWebView через Flutter-плагин.
Наблюдение и аварийный предел добавлены для безопасности эксперимента,
но до достижения предела события намеренно не исправляются.

Результат: после трёх подготовительных нажатий один Cmd+Enter дал
128 keydown; из них 127 дублей. Всего в запуске 131 keydown.

### A. «Только Enter»

После стандартной обработки WebKit возвращать «обработано» для Cmd+Enter,
чтобы остановить дальнейшую передачу этой конкретной комбинации.

```swift
let modifiers = event.modifierFlags.intersection(
  [.command, .control, .option, .shift]
)
let isCommandEnter =
  event.type == .keyDown &&
  modifiers == .command &&
  (event.keyCode == 36 || event.keyCode == 76)
// После оригинальной обработки WebKit:
// return isCommandEnter || originalHandled
```

36 и 76 обозначают Return и keypad Enter.
Подход привязан к одному сочетанию, а не к причине повторной доставки.

Cmd+Enter стал одиночным, но следующий Cmd+B дал 128 событий,
127 из них дубли. Поэтому A не подходит как общее исправление.

### B. «Маршрутизация»

Когда firstResponder находится внутри WKWebView, не отдавать событие
в стандартную обработку FlutterViewController, а направлять дальше
по нативной responder chain синхронно.

```swift
override func keyDown(with event: NSEvent) {
  if webViewHasFocus {
    nextResponder?.keyDown(with: event)
    return
  }
  super.keyDown(with: event)
}
```

В окончательном варианте аналогичная маршрутизация применяется
к keyUp и flagsChanged. Условие фокуса проверяется по цепочке responder:
не все события приложения обходят Flutter.

Первый исследовательский прогон B, где изменялся только keyDown,
не показал дублей. Полный raw-state этого раннего прогона не был сохранён.
После добавления keyUp/flagsChanged финальный полный прогон показал
15 дублей Shift+Escape. Связь изменения кода с расхождением пока не доказана:
возможна также зависимость от состояния фокуса/нативного маршрута.

В сбойном финальном прогоне максимальное число native Flutter-посещений
одной сигнатуры было 1, а WebKit-посещений 17.
Поэтому объяснение «любые оставшиеся дубли обязательно создаёт повтор
в очереди Flutter» недостаточно.

B оставляет браузер встроенным, но пока не является проверенным
универсальным исправлением.

### C. «Идентичность события»

Перед повторной обработкой в WKWebView проверяется, не видел ли он
уже тот же самый объект NSEvent.

```swift
let seen = NSHashTable<NSEvent>(
  options: [.weakMemory, .objectPointerPersonality]
)

func wasSeen(_ event: NSEvent) -> Bool {
  if seen.contains(event) { return true }
  seen.add(event)
  return false
}
// В режиме C перед оригинальной обработкой:
// if wasSeen(event) { return true }
```

Это не debounce по времени и не запрет двух быстрых одинаковых нажатий.
Новый объект события должен оставаться допустимым, включая события
легитимного удержания клавиши.

Однако Alt+Escape, Shift+Escape и Alt+Shift+Escape дали по два DOM-события.
Проверка идентичности на выбранной границе не гарантирует единственную
доставку в DOM: точный маршрут оставшихся дублей ещё нужно установить.

В лаборатории interception выполнен через подмену реализации
WKWebView.performKeyEquivalent (method swizzling).
Это диагностическая техника с широким действием внутри процесса,
не готовая рекомендация переносить такую подмену в production.

### D. «Нативное окно»

WKWebView помещается непосредственно в NSWindow без FlutterViewController
в цепочке обработки клавиатуры этого окна.

```swift
import Cocoa
import WebKit

let webView = WKWebView(
  frame: NSRect(x: 0, y: 0, width: 850, height: 650)
)
let window = NSWindow(
  contentRect: webView.frame,
  styleMask: [.titled, .closable, .resizable, .miniaturizable],
  backing: .buffered,
  defer: false
)
window.isReleasedWhenClosed = false
window.contentView = webView
window.makeKeyAndOrderFront(nil)
webView.load(URLRequest(url: url))
// Владелец окна должен удерживать window сильной ссылкой.
```

Существующее окно и WebView переиспользуются при повторном открытии.
Refresh начинает новый запуск. В финальной проверке повторное открытие D
сохранило run ID и счётчик 60 событий.

Основной прогон: 844 нажатия, 844 keydown, ноль дублей.
Финальный smoke-прогон: 60 нажатий, ноль дублей.

Это наиболее сильный кандидат при допустимости отдельного окна.
Он не доказывает, что embedded-взаимодействие исправлено,
и не заменяет проверку физической клавиатурой.

### E. «JavaScript-фильтр»

На странице отменяется стандартное действие Cmd/Ctrl-сочетаний:

```javascript
document.addEventListener('keydown', (event) => {
  if (event.metaKey || event.ctrlKey) {
    event.preventDefault();
  }
}, true);
```

Некоторые Cmd-сочетания перестали зацикливаться, но блокируются
обычные Select All/Paste. При проверке вставки поле не изменилось,
а автоматизация дождалась тайм-аута чтения clipboard приложением.

Alt+Escape всё равно вызвал 256 keydown, 255 дублей и аварийную остановку.
Кроме того, preventDefault не означает запрет всем JavaScript-обработчикам
страницы выполнять свою логику. E не подходит для произвольных сайтов.

## 8. Что именно покрыто тестами

Полная запланированная матрица: 74 клавиши x 16 комбинаций
Cmd/Ctrl/Alt/Shift = 1184 случая.

Клавиши: буквы, цифры, Return, keypad Enter, Tab, Escape, удаление,
стрелки, Home/End/PageUp/PageDown, пробел, пунктуация и F1-F12.

Автоматически отправлялись 844 относительно безопасных случая.
Перед каждым вводом Prompt снова получал фокус.
340 системных, оконных и функциональных случаев оставлены
для контролируемого ручного прогона: нельзя автоматически закрывать
приложение или менять системные настройки и считать это обычным тестом поля.

Ограничение инструмента: восемь сочетаний с клавишей equal без Shift
Computer Use доставил как Shift+Equal. Поэтому чистый прогон из 844 попыток
подтверждает наблюдение 836 разных ожидаемых сочетаний, а не 844.
В первичном B было 835 из-за пропущенного Ctrl+Shift+B;
последующая отдельная попытка зарегистрировала его.

Матрица показывает «событие наблюдалось», а не «вся семантика команды верна».
Например, наличие Cmd+B в счётчике не доказывает корректное форматирование текста.

Не сертифицированы:

- Физическое удержание клавиши и завершение repeat после отпускания.
- Разный порядок отпускания модификаторов.
- Смена раскладки, IME и ввод составных символов.
- Все 340 отложенных системных/оконных/функциональных случаев.
- Восемь физических equal-комбинаций без Shift.
- Все сценарии смены фокуса без повторного клика в Prompt.
- Весь жизненный цикл production-браузера TalkTo.

Автоматический тест не создавал DOM-события через dispatchEvent.
Однако автоматический ввод не равен физической клавиатуре,
особенно при исследовании нативных маршрутов событий.

## 9. Редактирование, фокус, сохранение результатов

В B и D проверены реальные изменения текста:
Select All, Paste, Undo, Redo. Undo возвращал предыдущий текст,
Redo восстанавливал вставленный текст; проверялись не только счётчики.

В B проверен переход WebView -> Flutter input -> WebView:
ввод в Flutter-поле и последующие обычная буква / Cmd+B на странице работали.

В E вставка блокировалась. Это функциональная регрессия.

Точность Copy/Cut, форматирование Cmd+B/Cmd+I/Cmd+U в contenteditable
и полный набор комбинаций после смены фокуса ещё требуют проверки.

Cmd+W не закрывал D в лаборатории, но в её MainMenu.xib отсутствует
Close shortcut. Это не засчитано ни как исправление, ни как новая
регрессия маршрутизации. Production-окну нужно настроить обычное меню.

Сводки шести вариантов сохранялись через native UserDefaults
и пережили перезапуск. Новая пустая сессия не должна затирать предыдущий
результат с событиями. Поздний отчёт после аварийной остановки может
уточнить счётчики, но не должен снова сделать запуск активным.

В live-state могут находиться ограниченные значения полей диагностической
страницы. Скрипт архивирования заменяет их длинами, чтобы не сохранять
текст clipboard в JSON-доказательствах. Сводки не содержат текста полей.

## 11. Гипотеза причины и границы знания

По исследованным исходникам рассматривается такое взаимодействие:

1. WebKit получает клавиатурное событие и не считает его обработанным.
2. WebKit возвращает событие в AppKit с временным флагом повторной передачи.
3. Flutter обрабатывает клавиши через асинхронный механизм.
4. К моменту последующей передачи события дальше временный флаг WebKit
   может уже быть снят.
5. Событие снова попадает в WebKit и может снова добраться до страницы.

Это рабочая гипотеза, не законченная трассировка конкретного сбойного
события. Для B с Shift+Escape она пока не объясняет всю картину.

Точки исходного кода для продолжения:

- [WebKit WebViewImpl.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/mac/WebViewImpl.mm):
  doneWithKeyEvent, _keyDownEventBeingResent, performKeyEquivalent,
  keyDown и повторная отправка через NSApp.
- [FlutterKeyboardManager.mm на исследованной revision](https://github.com/flutter/flutter/blob/6a19cca56475dbfba1478ee68d7bd0c2ef891da1/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterKeyboardManager.mm):
  очередь pending events, асинхронное решение handled,
  последующая передача nextResponder и _eventBeingDispatched.
- [FlutterTextInputPlugin.mm](https://github.com/flutter/flutter/blob/6a19cca56475dbfba1478ee68d7bd0c2ef891da1/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterTextInputPlugin.mm):
  собственная защита isDispatchingKeyEvent как ориентир для сравнения,
  а не готовый патч для WKWebView.

Ссылка WebKit main изменяется со временем и не доказывает точное
соответствие WebKit, поставляемому в установленной macOS.
Перед upstream-исправлением нужно привязать трассировку к фактической версии.

Пока нельзя честно утверждать ни «нам обязательно нужен fork Flutter engine»,
ни «достаточно этого Swift-фильтра для всех клавиш».

### Найденные upstream issues

[Flutter #170316](https://github.com/flutter/flutter/issues/170316),
открыт 2025-06-10. Похожее название про бесконечные keyboard callbacks,
но пример автора содержит собственную повторную отправку через NSApp.sendEvent.
Issue закрыт как invalid / not planned. Нельзя ссылаться на него как
на подтверждение, что именно наш дефект признан Flutter и уже исправлен.

[Flutter #189722](https://github.com/flutter/flutter/issues/189722),
открыт 2026-07-20: Accessibility keyboard events и постоянный redispatch loop
в FlutterKeyboardManager. Полезен для расследования автоматического ввода,
но тождество с нашим физическим Cmd+B и всеми WebView-дублями не доказано.

Наличие похожих issue не заменяет минимальное воспроизведение
и точную трассировку нашего случая.

## 12. Решение для TalkTo: что рекомендуем, но ещё не внедрили

Если отдельное окно macOS допустимо, D является предпочтительным
направлением по текущим данным.

Можно оставить embedded-просмотр на Android/iOS,
а для macOS реализовать нативное окно того же приложения.
Общие источники, conversation history и взаимодействие с Runtime
не должны дублироваться в Swift.

Предлагаемое разделение:

| Ответственность | Владелец |
| --- | --- |
| Что открыто: web / localHtml / localService | Общая модель браузера TalkTo |
| Conversation, долговременная история и синхронизация | Общий business-слой |
| Разрешение локального источника в доступный адрес | Существующий Runtime / bridge |
| Показ WKWebView, фокус, закрытие, оконное меню macOS | Нативный оконный компонент |
| Команды open/back/forward/reload и события навигации | Адаптер между Dart и Swift |

Технический URL страницы не должен подменять стабильную идентичность
локального файла или сервиса в истории. Нативное окно не отменяет
ранее согласованную модель открытия локальных источников.

Лабораторный D пока не реализует production-интеграцию:

- Back / Forward / Reload, адрес, загрузку и ошибки браузера TalkTo.
- Связь окна с conversation и запись навигации в общую историю.
- Downloads в согласованную папку компьютера через нужный механизм Runtime.
- Политику новых окон, внешних ссылок, разрешений и JavaScript-диалогов.
- Cookies / website data, upload file picker и восстановление состояния.
- Стандартные Cmd+W и меню, восстановление фокуса, корректное закрытие.
- Поведение при смене conversation и повторном открытии другого источника.

Это список интеграционной работы, а не утверждение,
что системный WKWebView не умеет соответствующие операции.

B/C сохраняют встроенный UX, но пока остаются исследовательскими кандидатами.
Замалчивать Escape-дубли или добавить ещё одно исключение только для Escape
не означает исправить механизм повторной доставки.

## 13. Следующий шаг расследования embedded-варианта

Если продолжаем B/C:

1. Зафиксировать версию macOS, SDK, плагина, способ ввода и режим.
2. Протрассировать один Shift+Escape через WKWebView.performKeyEquivalent,

6. Только после локализации выбрать уровень исправления:

## 17. Исследование B/C: продолжение 2026-09-25

Пользователь выбрал дальнейшее исследование встроенного WebView. Отдельное
нативное окно D пока не рассматривается как решение для TalkTo.

### Новые факты

- В отдельном прогоне C команда Alt+Escape привела к аварийной остановке:
  256 посещений WebKit и 257 входов в Flutter; страница получила 0 keydown.
  Нативные события имели timestamp `0`, а каждый проход представлялся
  новым объектом NSEvent. Текущая защита C по идентичности объекта не могла
  их распознать. При этом фокус страницы как нативного first responder
  не был подтверждён. Этот прогон не доказывает, что C также зациклится
  при физическом нажатии внутри сфокусированного Prompt.
- Доказательство: `evidence/c-repro-unfocused-alt-escape.json`.
- В предыдущем прогоне C с доставкой событий на страницу Alt+Escape,
  Shift+Escape и Alt+Shift+Escape дали по одному дублю. В его нативном
  отчёте Alt+Escape и Alt+Shift+Escape дважды вошли в Flutter с тем же
  объектом, а Shift+Escape вошёл в Flutter один раз. Поэтому одного
  фильтра повторов на входе Flutter недостаточно для всех трёх случаев.
- Предыдущий B с маршрутизацией keyDown/keyUp/flagsChanged получил
  16 событий страницы от одного Shift+Escape. Ранний B с одной только
  маршрутизацией keyDown не показал дублей, но полный raw-state того
  прогона не сохранился. Это расхождение теперь проверяется явно.

### Новые контрольные режимы

`B1` маршрутизирует за пределы асинхронной очереди Flutter только
`keyDown`. `keyUp` и `flagsChanged` проходят через штатный Flutter-код.
Старый `B` остаётся в приложении и не меняет свой смысл.

`C2` сохраняет защиту C на WKWebView.performKeyEquivalent и добавляет
отдельные проверки идентичности на WKWebView.keyDown и на входе
FlutterViewController.keyDown, когда фокус принадлежит WebView.
На каждой границе свой ledger. Общий ledger дал бы ложный дубль,
когда одно нормальное событие впервые проходит обе границы.
Старый `C` также остаётся отдельным контрольным режимом.

После первых живых проверок добавлен `B2`: маршрутизация `keyDown` как
в B1 плюс проверка повторного входа того же NSEvent в сфокусированный
FlutterViewController. В отличие от C2, B2 не отсекает повторный проход
WKWebView.performKeyEquivalent, необходимый некоторым командам редактора.

В нативной трассе теперь сохраняются стадия, keyCode, timestamp,
модификаторы, признак repeat, адрес объекта NSEvent и тип first responder.
Трасса ограничена последними 512 записями и не содержит введённого текста.
Чтение `eventNumber` было убрано: искусственные NSEvent без окна
выбрасывали исключение при обращении к этому свойству, отчего первый
прогон native XCTest упал ещё до проверки стратегии.

### Живые прогоны

Автоматический ввод сначала не доходил до страницы: accessibility-фокус
был, а нативного фокуса окна не было. Координатный click в Prompt перед
каждой комбинацией активировал окно. После этого `pressKey` давал
нативную трассу и DOM `keydown`; пустой ранний прогон не засчитывается.

### Выбор и следующий шаг

**B2 выбран как кандидат-победитель среди встроенных WebView-вариантов,
но не как готовый production-фикс.** Он единственный из B1/C2/B2 прошёл
